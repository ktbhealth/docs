`plugins/pages` serves **custom pages**: content stored in `pages` and
related documents, rendered on demand at clean URLs, with admin control
over publication, navigation, and ordering. Pages are data, not code —
no deploy needed.

## The model

| Column           | Meaning                                                        |
| ---------------- | -------------------------------------------------------------- |
| `path`           | Unique URL path (`/welcome`, `/faq`) — normalized             |
| `title`          | Display title                                                  |
| `richTextId`     | FK → `rich_text` document rendered as the page body            |
| `layoutId`       | FK → `layouts` row composing the body from ordered sections    |
| `builderJson`    | Versioned Puck document from the site builder (wins over layout slots) |
| `searchSchemaId` | FK → `schemas` row validating the page's URL search params     |
| `published`      | Only published pages render for visitors                       |
| `showInNav`      | Include in site navigation                                     |
| `sortOrder`      | Ordering within nav                                            |

A page picks one body source: `builderJson` if present, else the
`layoutId` composition, else the single `richTextId` document. All body
references are optional — a page with none renders an empty body.

## Path rules

`normalizePagePath` in `plugins/pages/src/service.ts` is the single
validator, applied both to admin input and to incoming request paths:

- Must start with `/`, no trailing slash (except root).
- Rejects whitespace, URL sigils (`?`, `#`, `*`), overlong paths.
- **Rejects the `/platform` namespace** — console paths belong to
  `panel.pages`, an app-context concern; custom pages can never shadow
  the admin console.
- The unique index on `path` is the backstop; the service also maps it to
  a friendly `PathTaken` error.

## Create and publish

Pages are managed through the plugin's admin surface at `/platform/pages`
(`panel.pages` contribution, server fns in `fns.ts`) — admin fns call
the service, which enforces publication state. Visitors only ever see
`published = true` rows through the wildcard descriptor; drafts are
invisible, not forbidden.

The console lists **both** sources: `pages` rows (editable here) and
pages plugins contribute via `pages`/`panel.pages` descriptors — those
render read-only with a **Provided by** badge naming the owning plugin
id, filtered by the plugin's package-granular enable state.

## Ordering and nav

`showInNav` + `sortOrder` drive the nav contribution (`chrome.tsx`). Keep
`sortOrder` dense (0, 1, 2…) — gaps are fine, duplicates resolve
consistently but are confusing to maintain.

## Schema changes

Standard flow: `schema.ts` → `bun run db:generate` →
`bun run db:migrate:local` → `bun run db:erd`. See the
[generated reference](/en/docs/developers/plugins/pages/reference).
