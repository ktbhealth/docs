Custom pages are resolved like filesystem routes but sourced from the
database — the design keeps content dynamic while the render path stays
boring.

## Request flow

1. The router's wildcard descriptor (`pages.render`, route key
   `pages.custom`) matches any unmatched path and hands it to the
   pages guard/loader.
2. The request path is normalized by the same `normalizePagePath` used
   for admin input — already URL-decoded, trailing slashes tolerated.
3. `publishedByPath` loads the row **only if `published = true`** —
   drafts and missing paths both produce the same not-found result.
4. The loader resolves the body references: `richTextId` → the parsed
   rich-text document, `layoutId` → ordered section slots (or the
   layout's `builderJson` Puck document when the layout was edited in
   the site builder), and `searchSchemaId` → validated URL search
   params. A page with `builderJson` renders that document; otherwise a
   layout-bound page composes its sections; otherwise the single
   rich-text document is the body.

## Why structured content, not markdown

Page bodies are stored as typed documents (`rich_text` rows, layout
sections, Puck `builder_json`) — never as raw markup. The renderer only
ever sees the parsed document shape, so stored content can't inject
components or scripts. If you need arbitrary code in a page, that's a
sign it should be a real route, not a custom page.

## The /platform reservation

`normalizePagePath` rejects the `/platform` namespace outright. Console
pages belong to `panel.pages` — an app-context contribution with its own
gate — so a custom page can never shadow admin UI or bypass the
`PlatformAdmin` check.

## Admin vs visitor asymmetry

Admins manage through `panel.pages` + server fns; visitors only ever hit
the published read path. There is no draft-preview URL — preview is the
admin list itself.
