RBAC is **dynamic**: roles are runtime-managed bundles of
`(resource, action, effect)` grants assignable to users and groups — not
compile-time config. Two packages share the work: `packages/rbac` (the
vocabulary + `Permissions` service) and `plugins/rbac` (tables, admin UI,
queries).

## The vocabulary

`packages/rbac/src/vocabulary.ts` holds `PERMISSION_CATALOG` — flat
`"resource.action"` strings like `patient.read`, `consultation.update`,
`platform.admin`. Entity actions live in `ENTITY_ACTIONS`, platform
actions in `PLATFORM_ACTIONS`. The catalog is currently
hand-synced (codegen is deferred) — **when you add a new permission, add it
here first** or role grants can't reference it.

## Create a role

Role metadata lives in `roles`; grants and assignments live exclusively
in `relation_tuples`:

- **Role grant** — `(objectType=<resource>, objectId="*",
  relation=<action>, subjectKind="role", subjectId=<role name>)`.
- **Membership** — `(objectType="role", objectId=<role name>,
  relation="member", subjectKind="user"|"group", subjectId=<id>)`.

The supported path is the `/platform` admin UI, which goes through
`RbacQueries`/`RbacCommands` — role edits validate grants against the
catalog (`isKnownPermission` warns on unknown entries) and writes are
CQRS-dispatched, never raw SQL.

## How checks resolve

At request time the `Permissions` service answers against the caller's
resolved grant set:

- `can(resource, action)` / `requirePermission(...)` — role-grant
  checks bound to the request `Principal`; fail closed with no
  principal.
- `canObject(objectType, objectId, relation)` — object-level ReBAC
  checks; `object_id = "*"` tuples are wildcard grants, `user`/`group`/
  `role` subjects expand (role subjects recurse through member tuples,
  depth-capped).
- `permissionsFor`/`canFor`/`requirePermissionFor` — the same checks
  bound to an explicit user id, for non-request contexts.

`permission_epoch` exists for cache invalidation: grant changes bump the
epoch so stale grant sets are discarded. `tenant_id` scopes tuples —
NULL is global, and `tenantPolicy` ("inherit"/"strict") selects whether
global tuples satisfy tenant-scoped checks. Deny entries never satisfy a
check — evaluation order matters, check `buildPermissions` in
`packages/rbac/src/index.ts`.

## Schema

Standard flow for table changes: `schema.ts` → `bun run db:generate` →
`bun run db:migrate:local` → `bun run db:erd`. See the
[generated RBAC reference](/en/docs/developers/plugins/rbac/reference).
