Dynamic RBAC resolves "may this subject do X?" at request time from
`relation_tuples` — the only grant store. The evaluation is deliberately
simple — the complexity lives in keeping the inputs fresh.

## The resolution path

```
relation_tuples (grants, memberships, object relations)
  → roles (metadata only — name, description, meta)
  → Permissions.can(resource, action) / canObject(...)
```

Two tuple encodings coexist:

- **Role grant** — `objectType` = resource (`"patient"`, `"platform"`,
  …), `objectId` = `"*"` wildcard, `relation` = action, `subjectKind` =
  `"role"`, `subjectId` = the role NAME (names are unique, so tuples
  survive role id changes).
- **Membership** — `objectType` = `"role"`, `objectId` = role name,
  `relation` = `"member"`, subject = the assignee (`"user"`/`"group"`).
  Group membership expands to the group's members; role subjects can
  nest (member tuples pointing at other roles) up to a depth cap.

Object-level checks (`canObject`) match tuples on
`(objectType, objectId, relation)` with `objectId = "*"` acting as a
wildcard across every object of that type.

## Scoping and expiry

- `tenant_id` NULL = global grant; set = tenant-scoped. With no tenant
  context only global tuples resolve; `tenantPolicy` "strict" hides
  global tuples from tenant-scoped checks, "inherit" lets them satisfy.
- `expires_at` bounds temporary grants — resolution honors it on hits,
  so expiry takes effect without a write.

## Deny semantics

Deny entries exist but **never satisfy a check by themselves** — they
subtract from broader allows (e.g. "admins except billing"). Evaluation
order matters; read `buildPermissions` in `packages/rbac/src/index.ts`
before assuming allow-wins.

## Epoch invalidation

`permission_epoch` is a single-row version counter bumped on every write
to `relation_tuples` (and group-membership-affecting tables). Grant sets
are cached per epoch — a bump invalidates all of them at once, which is
how revocations take effect without restarting anything.
