Páginas customizadas são resolvidas como rotas de filesystem mas com fonte
no banco — o design mantém o conteúdo dinâmico enquanto o caminho de
render permanece monótono.

## Fluxo do request

1. O wildcard descriptor do router (`pages.render`, route key
   `pages.custom`) casa qualquer path não reconhecido e o entrega ao
   guard/loader de pages.
2. O path do request é normalizado pelo mesmo `normalizePagePath` usado
   no input admin — já URL-decodado, trailing slashes tolerados.
3. `publishedByPath` carrega a linha **somente se `published = true`** —
   rascunhos e paths inexistentes produzem o mesmo resultado de
   não-encontrado.
4. O loader resolve as referências de corpo: `richTextId` → o documento
   rich-text parseado, `layoutId` → slots de seção ordenados (ou o
   documento Puck `builderJson` do layout quando o layout foi editado no
   site builder), e `searchSchemaId` → search params de URL validados.
   Uma página com `builderJson` renderiza esse documento; caso contrário,
   uma página ligada a layout compõe suas seções; senão, o documento
   rich-text único é o corpo.

## Por que conteúdo estruturado, não markdown

Corpos de página são armazenados como documentos tipados (linhas
`rich_text`, seções de layout, `builder_json` Puck) — nunca como markup
cru. O renderer só vê o formato do documento parseado, então conteúdo
armazenado não pode injetar componentes ou scripts. Se você precisa de
código arbitrário numa página, isso indica que ela deveria ser uma rota
real, não uma custom page.

## A reserva de /platform

`normalizePagePath` rejeita o namespace `/platform` diretamente. Páginas
de console pertencem a `panel.pages` — uma contribuição de app-context
com seu próprio gate — então uma custom page nunca pode sobrepor a UI
admin nem contornar a checagem `PlatformAdmin`.

## Assimetria admin vs visitante

Admins gerenciam via `panel.pages` + server fns; visitantes só atingem o
caminho de leitura publicado. Não existe URL de preview de rascunho — o
preview é a própria lista admin.
