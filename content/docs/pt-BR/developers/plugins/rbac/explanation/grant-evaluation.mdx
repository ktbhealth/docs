O RBAC dinâmico resolve "esse subject pode fazer X?" em request time a
partir de `relation_tuples` — a única store de grants. A avaliação é
deliberadamente simples — a complexidade está em manter os inputs
frescos.

## O caminho de resolução

```
relation_tuples (grants, memberships, relações de objeto)
  → roles (só metadados — nome, descrição, meta)
  → Permissions.can(resource, action) / canObject(...)
```

Duas codificações de tupla coexistem:

- **Grant de papel** — `objectType` = recurso (`"patient"`,
  `"platform"`, …), `objectId` = wildcard `"*"`, `relation` = ação,
  `subjectKind` = `"role"`, `subjectId` = o NOME do papel (nomes são
  únicos, então tuplas sobrevivem a mudanças de id do papel).
- **Membership** — `objectType` = `"role"`, `objectId` = nome do papel,
  `relation` = `"member"`, subject = o atribuído (`"user"`/`"group"`).
  Membership de grupo expande para os membros do grupo; subjects `role`
  podem aninhar (tuplas member apontando para outros papéis) até um
  limite de profundidade.

Checks em nível de objeto (`canObject`) casam tuplas em
`(objectType, objectId, relation)` com `objectId = "*"` funcionando como
wildcard sobre todos os objetos do tipo.

## Escopo e expiração

- `tenant_id` NULL = grant global; preenchido = com escopo de tenant.
  Sem contexto de tenant só tuplas globais resolvem; `tenantPolicy`
  "strict" esconde tuplas globais de checks com escopo de tenant,
  "inherit" deixa que elas satisfaçam.
- `expires_at` limita grants temporários — a resolução o respeita em
  hits, então a expiração tem efeito sem escrita.

## Semântica de deny

Entradas deny existem mas **nunca satisfazem um check por si só** —
existem para subtrair de allows mais amplos (ex.: "admins exceto
billing"). A ordem de avaliação importa; leia `buildPermissions` em
`packages/rbac/src/index.ts` antes de assumir que allow vence.

## Invalidação por epoch

`permission_epoch` é um contador de versão de linha única, incrementado a
cada escrita em `relation_tuples` (e em tabelas que afetam membership de
grupo). Grant sets são cacheados por epoch — um bump invalida todos de
uma vez, que é como revogações têm efeito sem reiniciar nada.
