Este tutorial adiciona um plugin mínimo ao repo `product`. Plugins são a
unidade de composição de features — rotas, serviços, tabelas e slots de UI
pendem de um objeto `Plugin`.

## Pré-requisitos

- O [ambiente de desenvolvimento](/pt-BR/docs/developers/apps/how-to/dev-environment)
  configurado.
- Leia [Arquitetura do produto](/pt-BR/docs/developers/kernel/explanation/product-architecture)
  primeiro se o layout do monorepo é novidade para você.

## Passos

1. **Crie o pacote.** Adicione `plugins/<name>/` com um `package.json`
   (`@ktb/<name>`, deps `workspace:*`) espelhando um plugin pequeno existente,
   como `plugins/notifications`.

2. **Defina o objeto plugin.** Em `src/index.ts`, exporte objetos plugin via
   `definePlugin` de `@ktb/kernel`:

   ```ts
   export const myFeaturePlugin = definePlugin({
     id: "my-feature",
     requiredDeps: [],
     // routes, services, tables, panel slots…
   });
   ```

   O registro é **por convenção** — `packages/app-host` descobre todo
   `plugins/*/src/index.ts` que exporta `plugins`. Nenhuma edição em registry
   central.

   Se o plugin contribui UI (itens de nav, slots de painel), adicione também
   `src/client.ts` exportando um array `plugins` com objetos de plugin
   **seguros para o cliente** — ele não pode importar código de servidor
   (nada de services Effect, db ou internals do `index.ts`).
   `@ktb/app-host/client` o descobre via `import.meta.glob`; a paridade entre
   `index.ts` e `client.ts` é verificada por `apps/web/src/plugins.test.ts`.

3. **Adicione superfície cross-plugin (opcional).** Se outros plugins
   precisarem dos seus dados, exporte grupos CQRS de `src/api.ts`
   (`Query.group`/`Command` de `@effect-server-utils/cqrs`) — nunca exponha
   leituras de tabela cruas. Veja [CQRS entre plugins](/pt-BR/docs/developers/kernel/explanation/cqrs)
   para o porquê.

4. **Adicione UI.** Rotas são TanStack file routes sob `src/routes/`; contribuições
   de nav e painel passam pelos extension points do plugin
   (`panel.headerActions`, etc.).

5. **Verifique.** `bun run check` na raiz, depois `bun run test` com escopo no
   seu pacote (`cd plugins/<name> && bunx vitest run`).

## Regras que vão te pegar

- Plugins **não podem importar de `apps/`** — a composição acontece em
  `apps/web/src/routes/` via objetos `api` injetados. Veja
  [Regras de arquitetura](/pt-BR/docs/developers/kernel/reference/arch-rules).
- Nada de `node:*`/`Bun`/`process`/literais de provider em código de plugin.
- Arquivos gerados (`routeTree.gen.ts`, output do paraglide, migrações drizzle)
  são regenerados, nunca editados à mão.
